# The engine protocol, version 1

A client plays a game over HTTP with JSON, and reads each turn as it happens
over Server-Sent Events. This document is the contract.
[`v1/openapi.json`](v1/openapi.json) is the same contract in machine-readable
form (OpenAPI 3.1): every request, every response body and every event's data.
Where the two disagree, that is a bug in one of them, and the engine's contract
tests (`test/contract/protocol_v1_test.rb`) check the engine against the JSON.

The protocol belongs to no engine in particular. Nothing in it names a
framework, a class or a table. An engine written in another language
implements this document, and a client written against it cannot tell which
engine it is talking to (except by `engine`, which is only for display).

Every endpoint's request and response, and every event's data, has an
example in the JSON; the contract tests hold each example to its schema and to
the shape of what the engine really sends.

## Revisions

- **1.1** adds `word` and `lines` to each verb, and `running_turn` to
  `standing`. Nothing was removed or changed in meaning.

## Rules that hold everywhere

- **Ids are opaque strings.** A client stores them and sends them back, and
  never parses, orders or builds one. An id is only meaningful inside the path
  it was issued under: a turn id belongs to one game.
- **Times** are ISO 8601 strings. **Money** is a JSON number of US dollars.
- **Prose is plain text.** Paragraphs are separated by blank lines. No markup.
- **Every enum is closed** and listed in the schema. Within v1, a new value may
  be added to an enum only where the schema says so. At the moment none does,
  so a value outside the list is an engine bug.
- **v1 only grows.** A field may be added to any object. No field is renamed,
  retyped or removed, and no required field becomes optional. A client must
  ignore fields it does not know. A breaking change is `/api/v2`, served
  beside v1.
- **Lists have a stated order**, given in the schema's descriptions. The
  panels' lists come in the order the engine recorded the things, never in
  query order and never sorted by name.

## Authentication

Every request carries `Authorization: Bearer <token>`. A token is issued to an
invited player by the engine's operator. There is no signup. A missing, wrong
or revoked token gets `401` with an `unauthorized` error and nothing else.

A player sees only their own games. A game id that belongs to someone else
answers `404`, exactly as an id that does not exist does. Worlds are shared.

## Errors

Every error body is `{"error": {"code": ..., "message": ...}}`. `message` is a
sentence for the player. `code` is one of:

| code | status | meaning |
| --- | --- | --- |
| `unauthorized` | 401 | no valid token |
| `not_found` | 404 | no such id, or not this player's |
| `limit_reached` | 402 | this month's spend limit is reached; the line was not accepted |
| `rate_limited` | 429 | more than the engine's turns per minute |
| `blank_line` | 422 | nothing was typed |
| `conflict` | 409 | the turn could not be accepted as sent |
| `unplayable` | 422 | the world cannot be played (its message says why) |
| `invalid` | 422 | a required field is missing |

## Spend

Every player has a monthly spend limit in US dollars. Before accepting a
line, the engine holds a fixed reservation for the turn, and it accepts the
line only if the month's metered spend, plus the reservation already held for
turns still running, plus this turn's reservation, stays within the limit.
Otherwise it answers `402 limit_reached`, and it records nothing and runs
nothing. Reading (every `GET`) keeps working at the limit. The month is the
calendar month in UTC. `GET /api/v1` reports `used_usd`, `held_usd`,
`limit_usd`, `turn_reservation_usd` and `period_ends_at`.

The same limit covers calls through the [model relay](relay.md): `used_usd`
includes the relay calls that have ended and `held_usd` the ones still open.

## Endpoints

| Request | Answers |
| --- | --- |
| `GET /api/v1` | `Service`: `protocol`, `version` (1), `capabilities`, `engine {name, version}`, `world_schema`, and the player's `spend` |
| `GET /api/v1/worlds` | `{worlds: [World]}`: the worlds a game can be started in |
| `GET /api/v1/games` | `{games: [Game]}`: the player's own games |
| `POST /api/v1/games` `{world}` | `201 Screen` for the new game, or `422 unplayable` |
| `GET /api/v1/games/{game}` | `Screen`: the game, the `glance`, the `standing` and the tail of the `log`. This is how a client draws a game it has just reconnected to. |
| `POST /api/v1/games/{game}/turns` `{line, request_token?}` | `202 {turn}`. The turn runs in the background. Errors: `402`, `409`, `422 blank_line`, `429`. |
| `GET /api/v1/games/{game}/turns/{turn}/events` | the turn, as Server-Sent Events |
| `POST /api/v1/games/{game}/interruptions/{turn}/acknowledge` | `{standing}` |

**`request_token`** makes a turn safe to retry. Sending the same line with the
same token again is the same turn, not a second one. Send a fresh token for
each new line. Without one, the engine picks one, and a retry becomes a new
turn.

**`standing`** says whether the game is `over` (and `ended`, the reason),
whether a turn is still `busy` (and `running_turn`, its id, so a client that
reconnects mid-turn opens that turn's events), and whether a `saved_turn`
needs the player.
Its `action` is `resume` (send its `line` again, with the saved turn's
request token, to finish it), `acknowledge` (an old turn that cannot be
resumed: the acknowledge endpoint lets it go and keeps its effects) or `none`.

**Verbs.** Each verb in the glance carries `word`, what follows the slash for
it: a client sends `/<word> <target>`, exactly as a target is named, and needs
no table of its own. `use` has no single word, because each of its targets is a
whole attempt ("Offer tide-slate to Ammon Brace; they may refuse"); instead its
`lines` gives, in the order of `targets`, the exact line that plays each one.
Send that line as it is.

**`capabilities`** names the parts of this document the engine serves:
`worlds`, `games`, `turns`, `turn_events`, `interruptions`, `spend_limit`. An
engine adds a name when it adds a capability.

## Turn events

`GET .../turns/{turn}/events` answers `text/event-stream`. Every event has an
`id` (its sequence number within the turn), an `event` name and one `data`
line of JSON:

| event | data | when |
| --- | --- | --- |
| `started` | `{turn, line}` | the engine has begun the turn |
| `prose` | `{turn, text}` | a piece of prose as it is written, to append |
| `glance` | `{turn, glance}` | the engine's facts changed during the turn (sent at most once, before the first prose) |
| `finished` | `{turn, outcome, refusal, resolved_by, rolls, text, notices, glance, standing}` | the turn is over; the stream closes |

**Redraw from `finished`, not from `prose`.** The streamed prose is a preview:
the text a turn saves can differ from what streamed, and a turn that falls
back to the engine's own words streams nothing. `finished.text` is the saved
record: the scene's prose, the refusal's sentence, or the engine's safety
notice. `notices` are the engine's own messages about the turn (a turn that
could not finish, say).

`outcome.kind` is what the turn did: `moved`, `talked`, `took`, `dropped`,
`read`, `attacked`, `threw`, `used`, `ended` (the story reached an ending),
`narrated` (anything else that was played), `refused` (the engine would not
play the line, and `refusal.kind` says why), `safety` (the engine stepped out
of the story, and `text` says why) or `failed`. `rolls` lists every die the
turn threw: `check` is a d20 `result` against a `target`; `break` is the die
thrown for a thing that came down on a floor, whose `result` at or under its
`target` broke it; and `blow`, `toll` and `fall` (a toll a fall took) report
the damage as `result`, with `die` and `target` null.

A fight is told once, when it ends, so an `attacked` turn whose round left
everybody standing has no prose of its own: its `text` is the engine's line
about the round just fought ("Round 1 is done: you struck ...") and its
`rolls` are that round's blows. A `failed` turn
always carries at least one entry in `notices` saying why.

**Resume.** If the connection drops, reconnect with `Last-Event-ID` set to the
last `id` received (or `?last_event_id=`). The engine sends only the events
after it. A finished turn replays in full to a request with no id. The engine
may close an idle stream, and the client then reconnects the same way.
Nothing is lost by reconnecting.
